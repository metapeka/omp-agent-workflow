Cache, sessions and handoff

A new session is a cold start. This page shows what the provider caches, what the plugin actually controls, and how a one-shot omp run silently broke a live handoff.

Measured on cline-pass/deepseek-v4.1-flash-1017 · 1M window · 2026-11-24

INCIDENT

2026-11-24. A short omp "say ok" run in the same directory overwrote .omp-handoff-session.json. The supervisor then treated the live session's handoff marker as stale, and the handoff stalled without a single warning. Read the postmortem.

TL;DR

  • A session is a JSONL history on disk. The model only sees the current context window.
  • Prompt caching reuses an unchanged prefix. Change the prefix, and everything after it is billed again.
  • Compaction rewrites history; handoff starts a new session. Both reset the cache.
  • The plugin does not create cache. It chooses when to keep the prefix and when to reset it, and it preserves state across the reset.
  • Tokens are measured, cache tokens are provider-reported, dollars are list-price estimates.

Three things people confuse

The same word “context” is used for a file, a window, and a cache. They behave differently.

How prompt caching works

A request is a prefix plus new messages. The prefix is the system prompt, tool schemas, and the conversation so far. If the provider has seen that exact prefix recently, it reuses the computation and reports the reused tokens as cache reads.

The important part for cost: a cache hit is not free, but it is much cheaper. On this model, input costs $0.30 per million tokens and a cache read costs $0.006 per million — 50× less. Cache writes are $0 here, but that is model-specific.

Providers differ in the details: Anthropic uses explicit cache breakpoints and a TTL, OpenAI and DeepSeek use automatic prefix caching. The common rule is the same: the prefix must match.

What counts as a prefix change A different model or provider, an edited system prompt, changed tool schemas, compacted history, or a new session with a different conversation. Appending a message does not break the cache; rewriting the middle of the conversation does.

What kills the cache

  • Model or provider switch. Kimi K3 → DeepSeek is a different cache namespace, a different tokenizer, and often a different window.
  • Compaction. The history is rewritten, so the next request has a new prefix.
  • Handoff. A new session file and a new conversation. The static system/tools prefix may hit, but the conversation does not.
  • Editing tools or the system prompt in the middle of a session.
  • Idle time beyond the provider TTL. The cache expires; the next turn is cold.
  • Provider-side eviction or routing. The client sends the same prefix, one request comes back with cacheRead 0, and the same prefix hits again seconds or minutes later. Read the next turn before blaming the prompt — see the 2026-11-27 case.

Where this plugin helps

The plugin does not sit inside the provider cache. It sits in the lifecycle: it watches context usage, warns, requests a handoff at a threshold, and keeps the session from stalling silently. In cache terms, it has exactly two reset points — handoff and fallback compaction — and it tries to make both deliberate.

What is measured vs estimated
  • Tokens — provider-reported usage on a completed turn. Exact for that provider and model.
  • Cache tokens — provider-reported cache read/write. Exact where the provider exposes them; a missing field is “not reported”, not “no cache”.
  • USD — OMP multiplies catalog prices by tokens (usage.cost.total). Fix list price, not an invoice: subscriptions, credits, discounts, and price changes are not included.
  • Context percent — OMP anchors on provider usage and counts the delta with its own tokenizer. Useful for thresholds, not a billing number.

Incident: the handoff that never happened

2026-11-24

One-shot run, one overwritten file, one stalled session. No supervisor warning, no retry, and the configured compaction fallback was blocked.

Configuration at the time

  • workflowMode=yoda-supervised, 1M window.
  • 18 / 25 / 30 / 60, handoffCooldownSeconds=900.
  • /handoff-new state limit: 64k characters.

What broke

  1. A short omp "say ok" run started in the same directory. It wrote its own entry to .omp-handoff-session.json, replacing the live session's terminal handle and session file. Its pid then exited.
  2. The live session wrote a handoff marker. The supervisor compared marker.sessionFile with the single record in the file, saw a mismatch, and classified the marker as stale.
  3. The handoff was never sent. handoffRequested stayed true, so the plugin did not retry, and auto-compaction was blocked while a handoff was “requested”.
  4. The state limit comment claimed 64k characters ≈ 16k tokens. Measured on Russian text it was 21–30k tokens.

What changed

VersionFixEffect
0.5.1532k state limit; supervisor and terminal-handle warnings; handoff retries; trimmed handle.The next stall is visible, and a missing marker triggers a retry.
0.5.16.omp-handoff-session.json is a {sessions} map keyed by pid; dead pids are pruned; supervisor selects by marker.sessionFile.A one-shot run can no longer steal a live session's handle. The live marker is not stale.
0.5.17Compaction fallback fires after retries are exhausted, or when a marker has no live supervisor.A broken handoff cannot disable the last-resort compaction forever.

After the fixes the happy path is unchanged: handoff at 30%, new session, cache warms again. The difference is the failure path: it now produces a warning and a fallback instead of a silent stop.

Case: the provider dropped a 252k prefix

2026-11-27

One turn came back with cacheRead 0 on a 252k-token prefix. Ten seconds earlier the same prefix was 99% cached; four minutes later it was 99.9% cached again. The client never changed the model, the thinking level, the tools or the system prompt.

Setup

  • Session dc_aievent — an orchestrator run: it spawned subagents with task and sat in wait while they worked.
  • Provider gateway cline-pass, model deepseek-v4.1-flash-1017, 1M window.
  • The gateway never reports cache writes: cacheWrite is 0 on every turn of that session, so only cacheRead is evidence here.

Four turns around the miss

The cold turn is the only one that carried the whole ~252k prefix as fresh input: 251 793 tokens in, 41 out, $0.0756 instead of the $0.0016–0.0041 of a warm turn — about $0.072 of overpay, 18–47× a normal turn. omp-cache-monitor reported it exactly as it is: hit 0% (input 251793, cacheRead 0, cacheWrite 0, prompt 251793). That warning is arithmetic, not a diagnosis.

Who is to blame

The provider side — the cline-pass gateway in front of deepseek-v4.1-flash-1017 — not OMP and not the plugin. Three facts point there, and each rules out a client cause:

  1. Not a rewritten prefix. Four minutes after the miss the same prefix was read from cache at its old size (251 776 ≈ 251 793). A prefix that really changed — model, thinking, tools/MCP, compaction — stays cold on the next turn instead of recovering.
  2. Not an idle TTL. The turn immediately after the first 4-minute pause was still 99% cached; the miss hit the next request ten seconds later.
  3. Not the subagents. Child sessions started warm: their first turns read 7 040–8 704 tokens of the shared system/tools head from cache. The parent's own turns around those same waits stayed at 99%.

What is left is the cache layer of the gateway: one request was routed to a backend that did not hold the prefix, or the prefix was evicted while several sessions and subagents were in flight. From the client those two look identical. The cache key, TTL and eviction belong to the provider, so a client cannot fix this — it can only notice it.

How to tell a provider miss from a real prefix change

  1. Look at the next turn of the same session. Hit again at a similar prefix size → provider miss. Still 0% → the prefix really changed.
  2. Measure the distance to the previous warm turn. A miss seconds after a 99% turn is not an idle TTL.
  3. Check whether cacheWrite is reported at all. A constant 0 on every turn means the gateway does not report writes; judge by cacheRead alone.

The omp-cache-monitor warning ends with “check the model, thinking, mode and MCP”. Here all four were unchanged — read that sentence as a prompt to look at the numbers, not as a verdict.

What a client can still do: keep the prefix shorter (a miss at 252k costs 7.5 ¢; at 60k, about 1.8 ¢) and treat repeated misses on one gateway as a provider issue rather than a configuration mistake.

Thresholds for a 1M window

All percentages are relative to the active model's window, not absolute token counts. The same numbers on a 100k model mean ten times fewer tokens.

Why 40%, not 60%? The fallback exists for the case where handoff does not happen. At 60% of a 1M window it is already 600k tokens — deep into the range where quality degrades. At 40% it is a real safety net, and in the normal path it never fires because handoff happens at 30%.

Checklist

  • Do not switch model or provider in the middle of a cache-sensitive task.
  • Keep the system prompt and tool schemas stable for the length of the session.
  • Handoff at a task boundary, not mid-edit and not mid-tool-loop.
  • Run the supervisor and watch for SUP OFF; a marker without a supervisor is not a handoff.
  • On a 1M window, set the fallback compaction to 40%, not 60%.
  • Use omp-cache-monitor for hit rate and tokens. Treat USD as a list-price estimate, not an invoice.
  • Treat thinking=off as a throttle, not a switch: on flash it cut reasoning ≈3.5×; on pro it changed nothing.
  • Budget from medians, reserve from ceilings; thinking blocks in the transcript are not billed tokens.
  • workflowMode=off disables the plugin and leaves OMP defaults: no status key, warnings, session info, or supervisor.
