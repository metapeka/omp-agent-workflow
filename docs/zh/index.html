缓存、会话与交接

新会话就是冷启动。这里说明提供方到底缓存什么、插件实际控制什么，以及一次性的 omp 运行如何悄悄破坏了正在进行的交接。

实测于 cline-pass/deepseek-v4.1-flash-1017 · 1M 窗口 · 2026-11-24

事故

2026-11-24。 同一目录下的短命令 omp "say ok" 覆盖了 .omp-handoff-session.json。守护进程因此把活跃会话的交接 marker 当成过期，交接静默停住，没有任何警告。查看复盘。

要点

  • 会话是磁盘上的 JSONL 历史。模型只看到当前上下文窗口。
  • Prompt cache 复用未变化的前缀。前缀一变，后面的内容重新计费。
  • 压缩会重写历史；交接会打开新会话。两者都会重置缓存。
  • 插件不制造缓存。它决定何时保留前缀、何时重置，并把状态带过重置点。
  • Token 是实测的，缓存 token 是提供方上报的，美元是按目录价估算的。

容易混淆的三样东西

“上下文”这个词同时指文件、窗口和缓存，但它们的行为完全不同。

是什么/handoff-new 之后OMP 重启之后切换模型之后
会话 磁盘上的 JSONL 历史，一个会话一个文件。 新文件；旧文件仍可恢复。 保留，可恢复。 保留，但按新模型重新分词。
上下文窗口 此刻发给模型的 token：system prompt、tools、消息。 新的小上下文，由交接状态构建。 从会话重建。 重建；窗口大小可能改变。
Prompt cache 提供方复用未变化的请求前缀。 通常为冷；相同的静态前缀可能命中，取决于提供方。 超过提供方 TTL 后为冷。 冷：缓存按模型/提供方区分。

Prompt caching 如何工作

一次请求由前缀加新消息组成。前缀包括 system prompt、工具 schema 和已有对话。如果提供方最近见过完全相同的前缀，它会复用计算结果，并把复用的 token 报告为 cache read。

成本上的关键：cache hit 不是免费，但便宜得多。这个模型 input 每百万 token $0.30，cache read 每百万 $0.006，便宜 50 倍。这里 cache write 为 $0，但这是模型特定的。

各提供方细节不同：Anthropic 使用显式 cache breakpoints 和 TTL，OpenAI、DeepSeek 使用自动前缀缓存。共同规则只有一条：前缀必须匹配。

什么算前缀变化 换模型或提供方、修改 system prompt、改动工具 schema、压缩历史，或者新会话带着不同对话。追加消息不会破坏缓存；重写对话中间部分会。

什么会杀死缓存

  • 切换模型或提供方。 Kimi K3 → DeepSeek 是不同缓存命名空间、不同分词器，通常窗口也不同。
  • 压缩。 历史被重写，下一次请求就是新前缀。
  • 交接。 新会话文件、新对话。静态 system/tools 前缀可能命中，对话不会。
  • 会话中途修改 tools 或 system prompt。
  • 空闲超过提供方 TTL。 缓存过期，下一轮为冷。

这个插件在哪里起作用

插件不在提供方的缓存内部。它位于生命周期上：观察上下文占用、发出警告、在阈值处请求交接，并防止会话静默卡死。用缓存的话说，它只有两个重置点——交接和回退压缩——并且尽量让两者都是有意的。

插件的覆盖范围，逐项说明

环节插件做什么对缓存的影响节省什么
普通轮次读取 getContextUsage()；不向 prompt 写入内容。无；前缀只追加。不制造额外 miss。
18% / 25%警告并建议交接。无；prompt 不变。在强制边界前完成任务的时间。
30%要求 agent 收尾并写 marker；守护进程发送 /handoff-new。一次重置。不把 300k+ 工作集继续带着走。
交接卡住最多重试 3 次，然后允许回退压缩。重试只追加；压缩是重置。避免静默卡死且回退失效。
Session info按进程在 .omp-handoff-session.json 中保留记录。无。不丢失活跃会话的 terminal handle。
cache-monitor外部插件：命中率、token、成本。无；只读。用数据而非猜测来设阈值。
插件之外 提供方 TTL、缓存键、分词器、模型切换，以及是否修改 tools 或 system prompt。插件可以让重置变得有意；它无法让冷前缀变热。

哪些是实测，哪些是估算
  • Token — 完成轮次的 provider-reported usage。对应该提供方和模型是准确的。
  • 缓存 token — 提供方上报的 cache read/write。提供方有该字段时准确；字段缺失表示“未上报”，不是“没有缓存”。
  • USD — OMP 用目录价乘以 token（usage.cost.total）。这是固定目录价，不是账单：订阅、额度、折扣和调价都不包含。
  • 上下文百分比 — OMP 以 provider usage 为锚点，用本地分词器补算增量。适合做阈值，不适合对账。

事故：没有发生的交接

2026-11-24

一次一次性运行，一个被覆盖的文件，一个卡住的会话。 没有守护进程警告，没有重试，配置好的回退压缩也被阻塞。

当时的配置

  • workflowMode=yoda-supervised，1M 窗口。
  • 18 / 25 / 30 / 60，handoffCooldownSeconds=900。
  • /handoff-new 的状态上限：64k 字符。

出了什么问题

  1. 同一目录启动了一个短命令 omp "say ok"，向 .omp-handoff-session.json 写入自己的记录，覆盖了活跃会话的 terminal handle 和 session file。随后它的 pid 退出。
  2. 活跃会话写入交接 marker。守护进程把 marker.sessionFile 与文件里唯一的记录比较，发现不一致，判定 marker 过期。
  3. 交接从未发送。handoffRequested 保持 true，插件不再重试；而自动压缩在“已请求交接”时被阻塞。
  4. 状态上限的注释声称 64k 字符 ≈ 16k token。俄语文本实测为 21–30k token。

改了什么

版本修复效果
0.5.15状态上限 32k；守护进程和 terminal handle 警告；交接重试；handle trim。下一次卡住可见；marker 缺失会触发重试。
0.5.16.omp-handoff-session.json 改为按 pid 的 {sessions} 映射；清理死 pid；守护进程按 marker.sessionFile 选择记录。一次性运行不能再抢走活跃会话的 handle，活跃 marker 不再被判过期。
0.5.17重试耗尽后，或 marker 没有存活守护进程时，回退压缩生效。损坏的交接不能永久禁用最后一道保险。

修复后正常路径不变：30% 交接、新会话、缓存重新变热。区别在失败路径：现在会给出警告和回退，而不是静默停住。

1M 窗口的阈值

所有百分比都相对于当前模型的窗口，不是绝对 token 数。同样的数字在 100k 模型上意味着十分之一的 token。

为什么是 40%，不是 60%？ 回退是为“交接没有发生”准备的。在 1M 窗口上，60% 已经是 600k token，早就进入质量下降区。40% 才是真正的保险；正常路径下它在 30% 交接后就轮不到触发。

检查清单

  • 对缓存敏感的任务，不要中途切换模型或提供方。
  • 整个会话期间保持 system prompt 和工具 schema 稳定。
  • 在任务边界交接，不要在编辑中途或工具循环里交接。
  • 运行守护进程并留意 SUP OFF：没有守护进程的 marker 不是交接。
  • 1M 窗口上把回退压缩设为 40%，不要设 60%。
  • 用 omp-cache-monitor 看命中率和 token。USD 是目录价估算，不是账单。
