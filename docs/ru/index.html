Кэш, сессии и handoff

Новая сессия — это холодный старт. Здесь видно, что кэширует провайдер, чем реально управляет плагин и как одноразовый omp тихо сломал живой handoff.

Замерено на cline-pass/deepseek-v4.1-flash-1017 · окно 1M · 2026-11-24

ИНЦИДЕНТ

2026-11-24. Короткий запуск omp "say ok" в том же каталоге перезаписал .omp-handoff-session.json. Supervisor счёл marker живой сессии устаревшим, и handoff завис без единого предупреждения. Разбор ниже.

Коротко

  • Сессия — это JSONL-история на диске. Модель видит только текущее окно контекста.
  • Prompt cache переиспользует неизменённый префикс. Меняешь префикс — всё после него оплачивается заново.
  • Компакция переписывает историю; handoff открывает новую сессию. Оба сбрасывают кэш.
  • Плагин не создаёт кэш. Он выбирает, когда сохранить префикс, а когда сбросить, и переносит state через сброс.
  • Токены измеряются, cache-токены отдаёт провайдер, доллары — оценка по list price.

Как работает prompt caching

Запрос — это префикс плюс новые сообщения. Префикс: system prompt, схемы инструментов и вся история. Если провайдер недавно видел ровно такой префикс, он переиспользует вычисления и показывает переиспользованные токены как cache read.

Главное про деньги: cache hit не бесплатный, но намного дешевле. На этой модели input стоит $0.30 за миллион токенов, cache read — $0.006 за миллион, в 50 раз меньше. Cache write здесь $0, но это свойство конкретной модели.

Детали у провайдеров разные: Anthropic использует явные cache breakpoints и TTL, OpenAI и DeepSeek — автоматическое кэширование префикса. Общее правило одно: префикс должен совпасть.

Что считается изменением префикса Другая модель или провайдер, отредактированный system prompt, изменённые схемы tools, сжатая история или новая сессия с другим диалогом. Добавление сообщения в конец кэш не ломает; перезапись середины диалога — ломает.

Что убивает кэш

  • Смена модели или провайдера. Kimi K3 → DeepSeek — другое пространство кэша, другой токенизатор, часто другое окно.
  • Компакция. История переписана, у следующего запроса новый префикс.
  • Handoff. Новый файл сессии и новый диалог. Статический префикс system/tools может попасть, диалог — нет.
  • Правка tools или system prompt посреди сессии.
  • Простой дольше TTL провайдера. Кэш истекает, следующий ход холодный.

Где помогает этот плагин

Плагин не сидит внутри кэша провайдера. Он сидит в жизненном цикле: следит за заполнением контекста, предупреждает, просит handoff на пороге и не даёт сессии тихо встать. В терминах кэша у него ровно две точки сброса — handoff и fallback-компакция — и обе он старается делать осознанными.

Что измерено, а что оценено
  • Токены — provider-reported usage завершённого хода. Точны для этого провайдера и модели.
  • Cache-токены — cache read/write от провайдера. Точны там, где провайдер их отдаёт; отсутствие поля — «не сообщается», а не «кэша нет».
  • USD — OMP умножает цены каталога на токены (usage.cost.total). Это фиксированный list price, не счёт: подписки, кредиты, скидки и смена цен не учтены.
  • Процент контекста — OMP якорится на provider usage и досчитывает дельту своим токенизатором. Для порогов годится, для бухгалтерии — нет.

Инцидент: handoff, которого не было

2026-11-24

Один одноразовый запуск, один перезаписанный файл, одна зависшая сессия. Без предупреждения supervisor, без повтора, а настроенный fallback-компакции был заблокирован.

Настройки на тот момент

  • workflowMode=yoda-supervised, окно 1M.
  • 18 / 25 / 30 / 60, handoffCooldownSeconds=900.
  • Лимит state для /handoff-new: 64k символов.

Что сломалось

  1. В том же каталоге запустился короткий omp "say ok". Он записал свою запись в .omp-handoff-session.json, заменив terminal handle и session file живой сессии. Его pid затем завершился.
  2. Живая сессия поставила marker. Supervisor сравнил marker.sessionFile с единственной записью в файле, увидел расхождение и признал marker устаревшим.
  3. Handoff не отправился. handoffRequested остался true, поэтому плагин не повторил запрос, а авто-компакция была заблокирована, пока handoff «запрошен».
  4. Комментарий к лимиту state утверждал, что 64k символов ≈ 16k токенов. На русском тексте замер дал 21–30k токенов.

Что изменилось

ВерсияИсправлениеЭффект
0.5.15Лимит state 32k; warning про supervisor и terminal handle; повторы handoff; trim handle.Следующий сбой виден, отсутствие marker вызывает повтор.
0.5.16.omp-handoff-session.json — карта {sessions} по pid; мёртвые pid вычищаются; supervisor выбирает по marker.sessionFile.Одноразовый запуск больше не крадёт handle живой сессии. Её marker не считается stale.
0.5.17Fallback-компакция срабатывает после исчерпания повторов или если marker остался без живого supervisor.Сломанный handoff больше не отключает последнюю страховку навсегда.

После фиксов happy path прежний: handoff на 30%, новая сессия, кэш снова прогревается. Отличается путь сбоя: теперь он даёт warning и fallback, а не тихую остановку.

Пороги для окна 1M

Все проценты считаются от окна активной модели, а не в абсолютных токенах. Те же числа на модели с окном 100k означают в десять раз меньше токенов.

Почему 40%, а не 60%? Fallback нужен на случай, когда handoff не состоялся. На 1M окне 60% — это уже 600k токенов, глубоко в зоне деградации. 40% — реальная страховка, а в нормальном пути она не срабатывает, потому что handoff происходит на 30%.

workflowMode=yoda-supervised
contextWarnPercent=18
contextSuggestPercent=25
handoffAtPercent=30
autoCompactPercent=40
handoffCooldownSeconds=900

Чек-лист

  • Не менять модель или провайдера посреди задачи, если кэш важен.
  • Держать system prompt и схемы tools стабильными на всю сессию.
  • Делать handoff на границе задачи, не посреди edit и не внутри tool-loop.
  • Запускать supervisor и следить за SUP OFF: marker без supervisor — это не handoff.
  • На окне 1M ставить fallback-компакцию на 40%, а не на 60%.
  • Смотреть hit rate и токены в omp-cache-monitor. USD — оценка по list price, не счёт.
